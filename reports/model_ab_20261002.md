# MiMo 与 DeepSeek 小样对照（2026-10-02）

## 结论

本轮 DeepSeek 的速度优势明显，6 题完整管线的小样得分也较高。固定证据的 8 题，两组答案值均正确，DeepSeek 在两题的引用上失分。建议继续扩大相同题目的完整管线对照，暂不根据这组回归题推断全量训练集或 Kaggle 公榜分数。

全部请求均已结束。此次不修改生产代码、提示词、模型选择配置、索引或图片描述缓存，不覆盖已有提交文件，也未提交／推送。

### q029：两组均有正确证据，但选用了不同口径

- 两组都召回了 `li2025b:text:30`，其中包含标准计算需要的美国发电平均耗水量；AWS 的 WUE 0.18 也都取得了。
- MiMo 选择 `talukder2026:text:19` 的 1.8 L/kWh，输出 1.8 / 0.18 = 10。模型说明明确写了 excluding hydroelectricity，但没有拒绝这一范围受限的操作数。
- DeepSeek 选择 `shehabi2024:text:204` 的 4.52 L/kWh，输出 4.52 / 0.18 = 25.1。其操作数属于数据中心用电对应的间接耗水口径，未选择题目对应的 3.1 L/kWh。
- MiMo 完整管线与固定证据对照的证据哈希、查询列表均相同，答案却分别为 10 和 17.4。此次失败不能全部归到检索覆盖，生成阶段的条件选值仍有波动。程序复算只能确认运算过程，无法保证模型选择了正确口径。

### q274：术语改写影响精确文本证据的覆盖

- MiMo 的查询基本重复原问，没有加入 Extractive QA 的明确术语；最终证据缺少 `luccioni2024:text:38`，从 Fig.1 下须读出约 0.2，数值错误。
- DeepSeek 改写中加入 extractive question answering，召回 `luccioni2024:text:38` 的直接报告值 0.3，回答通过。
- 这个成功同时涉及查询规划与证据选择，不能据此单独认定 DeepSeek 的原图读数更准确。

## 3. 配置、计时异常与边界

- 模型为 `mimo-v2.6-flash` 与 `deepseek-flash`，成功响应返回的模型名与配置一致。两组均沿用 `temperature=0`、关闭思考、`timeout=120`、`max_retries=2`，未设置新的输出上限。两家默认输出预算可能不同，实验比较当前实际客户端配置。
- MiMo 完成请求的用量报告均为 reasoning_tokens=0；DeepSeek 的该用量字段未返回，不能把缺失字段视为服务端对零思考 token 的额外证明，其请求已显式关闭思考。
- 每题两个供应商串行，调用次序按固定题号顺序交替，不同题最多三路并发。完整管线分两批运行，分别为两题、四题；已有逐图并发及检索锁保持不变。
- q104 的 MiMo 一次独立读图逻辑调用耗时 373.32 秒，完成响应的 reasoning_tokens=0。该计时包含 SDK 内部等待／重试，当前记录无法继续拆分服务端处理与网络等待。没有删除慢结果，也没有重跑后替换原记录。
- 完整管线首次冷启动卡在 Hugging Face 的模型 HEAD 联网检查，该诊断进程在题目请求前终止。随后仅在诊断子进程中开启离线缓存读取，加载现有 BGE 模型，未安装／下载模型，未改变 `.env` 或生产配置。
- 样本来自既有回归题，含已知难题；未随机抽取，且每组只运行一次，模型输出、服务负载与网络均可能波动。六题／八题得分均为本地训练题得分，不能直接与 Kaggle 公榜 0.896 比较。
- 现有向量库和图片描述仍保持 MiMo 建库时的内容。本轮未比较两模型的离线图片描述质量，也未比较视觉向量检索。
